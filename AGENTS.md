# Ownership
- Claude Code owns engineering: architecture, implementation, refactoring, API integration, tests and security.
- Antigravity owns visual UI/UX design and design specifications only, and must not make architectural or business-logic changes to the production source; approved designs are implemented by Claude Code.
- The CMS repository (`../CMS_HMV`) is read-only from this project unless explicitly approved.

# Architecture rules
- Follow the structure and dependency rules in `docs/architecture.md`: one module per route in `src/views` (renamed from `src/pages`, which Next.js reserves), reusable business functionality in `src/features`, site chrome in `src/components/layout`, business-agnostic primitives in `src/components/ui`; delete unreachable code instead of keeping it.
- Use locale-free React Router URLs (language from `?lang=`/stored preference; legacy `/en`, `/vi` prefixes redirect) and a shared bilingual content module; this keeps overview and detail pages consistent without duplicating layouts.
- Use Helmet for route head links and language attributes, and synchronize route titles/meta tags to the static fallback explicitly; this avoids duplicate React 19 metadata while preserving crawlable sitewide tags.
- Keep images as files under `src/assets` imported by the bundler; no remote asset manifests or host-specific asset proxies. Exception: EcoNews in CMS mode renders the absolute media URLs (with their width/height) that the CMS public API returns.
- Keep layout CSS separate from global theme tokens; this preserves the authoritative semantic palette while isolating the editorial page styling.
- Serve photographs from bundled `src/assets` files with explicit width/height matching the real image and lazy loading below the fold; this avoids layout shifts.
- Keep product photography in a shared product-ID mapping with source and subject metadata; overview and detail pages must use the same verified product image.
- EcoNews and CMS-managed pages (About) may read the HMV CMS **public** API (`/api/v1/public/*`) in CMS mode only (`features/articles`, `features/pages`, shared client in `lib/cms.js`; see `docs/cms-integration.md`): no credentials, no admin routes, no fallback to bundled content when the CMS fails.
- The product-page RFQ and the contact form are validated client-side and handed to the visitor's email app via a shared mailto builder; their UI must say a draft was prepared, never that a request was sent. The homepage Quick RFQ (`features/inquiries/QuickRfq`, the fast lane, mounted once, as the strip `HomeQuickRfq` directly below the hero and never over its photograph; calls to action reach it with `focusQuickRfq()`, never a second copy of the form) is not one of them: it is a server submission into the same lead pipeline as the Trade Desk (below), says "received" only after the API accepted the inquiry, and offers the mailto draft only after a failed send.
- The HMV Trade Desk (`features/trade-desk`) is the primary inquiry path: UI → `@/lib/inquiry` port → `POST /api/inquiry` (Next.js) → validation → inquiry service → delivery adapter (`src/next/inquiry`); it says "sent" only after the API accepted the inquiry. The Vietnam–Cambodia route assessment (`POST /api/route-assessment`, `features/route-assessment`) is the other server submission, through the same port, service and adapter, under the same rules; its contract stays separate from the Trade Desk's. Requirements come from controlled rules (`rules.js`), never generated. The Quick RFQ is the second way into that same `POST /api/inquiry` (no second endpoint, webhook or contract): it reuses the desk's rules, validation, fingerprint and idempotency key (`trade-desk/submission.js`) and the visit context, and can hand what the buyer already typed (product, destination, volume) to the desk through `openTradeDesk()`. Analytics go through `lib/analytics.js` only: allow-listed categorical events, no personal data or free text.
- Keep homepage service summaries separate from full detail sections and use a native scroll-snap activities carousel with visibility-aware automatic advancement and pause/interaction/reduced-motion safeguards; this limits homepage density and supports touch without another carousel dependency.

- Keep hero stock imagery in its own asset pointer, separate from HMV evidence photographs, with CSS-only motion and reduced-motion support; this preserves provenance and avoids scroll-rendering overhead.

- Golden passion fruit has one page per buyer segment (International Buyers at the product's own URL, Foodservice, Retail Business; `PRODUCT_SEGMENTS` in `src/i18n/routes.js`, copy in `data/passionFruitPages.js`, photographs in `data/passionFruitMedia.js`, details and the media register in `docs/architecture/PASSION_FRUIT.md`). They sell to businesses only: no prices, cart or consumer funnel. They state nothing HMV cannot document (no certification, Brix, grade, capacity, packaging of HMV's own, customers); every inquiry goes through the Trade Desk or the Quick RFQ, and the buyer segment is read from the source page, never a new payload field (the pages hand it to the desk and the Quick RFQ as `segment`, which words the volume question and chooses the units: kilograms for hospitality and retail, `unitsFor` in `trade-desk/rules.js`; no other product's units change). The pages import only the tracked WebP derivatives of `scripts/passion-fruit-images.mjs`; the supplied JPG and PNG originals stay untracked.

- **Supplier confidentiality (mandatory).** HMV Global is the single commercial point of contact between its supply network and its buyers: every inquiry, quotation and supply conversation goes through the HMV Trade Desk, the Quick RFQ or HMV's official channels, never to a supplier. By default the public site, its data, its build output and this repository carry no supplier identity, logo, contact, website, precise farm or facility address or coordinates, purchasing price, supplier quotation, contract, margin or customer data, and no photograph of identifiable people without clearance; third-party farms, factories and warehouses are never presented as HMV's. This repository is public and is not a media archive: supplied source photographs, documents and design references stay local (untracked and ignored: `.gitignore`), and only inspected, sanitized derivatives (cropped or edited without supplier marks, ASCII names, no EXIF or GPS) are committed, generated by a script. If supplier information cannot be removed from an image, the image is withheld. Confidentiality is a server-side data boundary, not a visual one: hiding an element is not protection, and nothing confidential may reach a client bundle, a public JSON file, metadata, structured data, analytics, an error message or the sitemap; internal supplier data, when it exists, lives behind authenticated server-side authorization and never in a public CMS endpoint. The Trade Desk answers a request for a supplier's identity or contact as HMV's representative (`asksForSupplier`, `copy.js`) and directs traceability or compliance requests to HMV's commercial team; legally required traceability, regulatory disclosure and authorized buyer due diligence stay supported through controlled business processes, never through a false answer.
- **Selective staging.** With private source files in the working tree, stage by explicit path (`git add src/features src/data docs`), never `git add .`, `-A`, `-u` or a bare `src`, and read `git diff --cached --name-only` before every commit. `npm run lint` runs `scripts/check-protected-assets.js`, which fails when a source photograph, a private design reference or a supplier or customer document is tracked (an allowlist: visual baselines, favicon, Open Graph image); a new approved public raster file is added to that allowlist in a reviewed change.
